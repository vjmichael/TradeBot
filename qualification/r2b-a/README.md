# TB-SEC-KEY-01-R2B-A — Independent Kraken Spot permission verifier candidate
2026-11-20. Development-only candidate in the non-merge qualification/recovery branch. D2 production tree remains unchanged. Not installed or enabled.

References: Kraken official Get API Key Info (https://docs.kraken.com/api/docs/rest-api/get-api-key-info) and Spot REST Authentication (https://docs.kraken.com/exchange/guides/rest/authentication), checked 2026-11-20. The dedicated inspection endpoint requires no key permissions. It returns account/key metadata and actual scope names, so the response must not enter general application logs or IPC.

## Candidate behavior
- Fixed POST to api.kraken.com /0/private/GetApiKeyInfo only, direct certificate-validated TLS, no redirect/proxy/automatic retry or caller-selected endpoint. Secret used only to sign. Bounded response bytes and socket timeout; total wall deadline and independently enforced egress are still integration requirements.
- Conservative proposed initial spot profiles: read = query-funds, query-open-trades, query-closed-trades, query-ledger; trade = same plus modify-trades and close-trades. Exact allowlists, no withdrawals/deposits/earn/withdrawal-address management/unknown or extra permissions. No funding or order endpoint exists in the verifier. Review profile against eventual approved engine scope before release; do not enlarge silently.
- Refuse malformed/ambiguous responses, missing scopes, returned key mismatch, expiration and restricted history. Validate reported IP allowlist format but do not assert IP-policy adequacy, account identity equivalence, or current provider availability beyond the inspection. Fixed sanitized codes only; never return provider error strings, account labels, IBAN, keys or signatures. No 2FA handling yet: requests requiring OTP fail unverified.
- Verification is separate from trading authorization. A status-only receipt has role, vault-issued opaque generation, check time and expiration (maximum five minutes, shorter when key expires). Receipt invalid on role/generation/time mismatch. No durable receipt or authority is granted by this standalone Python object.
- Trusted custody integration must issue and monotonically manage generation/nonce, serialize requests for the same key across processes and reboot, enforce key-pair role separation and refuse same key across roles, atomic replacement/removal and stale results, independent authenticated operator admission, provider-side revocation check with safe pause, current trusted time, hard request deadline and bounded backoff, receipt provenance/tamper defenses, OS-level isolated credential execution and constrained egress. Do not provision trading credentials before full R2A/R2B and financial release gates. Graphical status/test/remove/replacement and same-account binding remain open.
