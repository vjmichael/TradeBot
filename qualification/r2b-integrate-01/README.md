### Shared lifecycle
1. Authenticated operator previews enroll/replace/remove/disable; no network or financial side effect on preview or cancellation. Commit paired encrypted material and opaque version/binding atomically with metadata in existing BEGIN IMMEDIATE transaction. Replacement/remove/disable/policy change invalidates current receipts and pending review. Retain Kraken nonce history; reject duplicate Kraken key roles and duplicate Telegram bot IDs.
2. Independent operator explicitly reviews Test connection with provider, role, current credential generation and exact policy/recipient. Trusted service admits one pending attempt; serialize by key and role across processes, replacement/removal and restarts. Persist immutable attempt and consume authorization before network; no browser/AI supplied raw receipt. Retain durable per-key request sequencing and send-intent rules from prior contracts.
3. Only fixed provider-specific adapter receives required credential inside authorized custody; enforce exact host/method/path, TLS, independent egress and hard total deadline. No automatic redirects, arbitrary prompt or financial action. Telegram test is exactly a fixed role-specific message, not a heartbeat or command; Grok metadata test is not inference. Independent resource/queue admission and bounded cooldown. Unknown delivery/order outcome is never a reason to retry automatically.
4. Commit trusted receipt only if current role/version/binding/policy/attempt/authorization still match. Separate observation categories: Kraken scope verification, Telegram provider acceptance vs explicit human acknowledgement, Grok metadata verification vs actual inference capability. Initial 300-second maximum current receipt window; preserve historical sanitized test time/outcome separately, label expired and stale. Do not equate a diagnostic projection with an authoritative receipt, activation, live authorization or operator identity.
5. Restart, integrity failure and trusted clock uncertainty invalidate current verification until safely requalified; no implicit reset or restored stale trust. R2C must qualify backup rollback protection and nonce continuity. Revoke local access on disconnect; actual remote revocation is separate. Display status only to normal dashboard; recipient preview only on separately authenticated operator surface. Never emit secrets, provider body, raw error, identifiers, URLs containing tokens or account PII.

## Persistent connectivity strip (user-directed)
A compact bottom-of-app label must be available on every normal screen, including local/offline states, with accessible plain-text status and a single details/Retry control. Show **Server connection** independently from **Server internet** and per-provider tests. Distinguish dashboard-to-VPS reachability (local client may be offline, server down or network path unavailable; do not pretend which unless independently observed), VPS no route, DNS/TLS trouble, multiple approved internet origins unreachable, single provider failure, and unknown/stale. A fresh successful external contact does not mean all services work. A failed request does not prove a global internet outage. A stale provider test does not prove internet failure. Keep last known observation time separate from current status. Never display an old green label on stale evidence. Browser offline hint is advisory only; do not infer VPS internet condition from it.

Use lightweight observations from existing permitted public market-data service/health checks, distinct reviewed origins, and local non-secret network status; no extra third-party beacon, paid inference, credentialed probes or PII egress for routine monitoring. If evidence insufficient, show unknown rather than guessing. Candidate freshness 60 seconds for network observations and 300 seconds for provider test view; review against measured workload and deadlines under RESOURCE-02. Source observation ages must be normalized using a trusted time/monotonic basis; client and server clocks cannot be naively compared. The offline client can display lost server connectivity without a fresh server response. Observe and debounce bounded transitions; reuse supervisor/scheduler, no new always-on polling daemon. Explicit manual retry respects rate/cost budgets; routine reconnect never submits financial orders or sends test bot messages. Financial Gate still independently determines whether safe new entries can be admitted, and protection/reconciliation remains independently supervised. Do not guarantee exits during an outage.

Recovery Bot uses independent heartbeat monitoring in TB-09; same failed VPS cannot reliably send its own outage alert. External observer may alert when heartbeat missing but must not claim cause without evidence. Separate bot identity and narrow privileges; no remote restart authority added. No additional hosting or paid services authorized here.

## Implemented diagnostic projection
connection_status.py is pure Python, no I/O, no authorization, no service loop. It projects trusted typed observations to separate dashboard and host-network statuses. A single failed probe is insufficient for offline claim; contradictory and stale evidence remain uncertain. Provider outcomes require enabled role, current generation/policy and current bounded timestamps and exact role-specific allowlist; unknown status cannot leak raw strings. Telegram API acceptance and human acknowledgment remain distinguishable. The fixture assumes trusted, independent origin evidence and current inputs; those collection, persistence, timing, authentication and freshness responsibilities remain with installed integrations. Expired receipt cannot become authoritative through this projection; durable monotonic clock and invalidation belong to vault. Not a replacement for any provider adapter.
