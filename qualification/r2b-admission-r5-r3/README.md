**Status: R5-R3A and R5-R3B-R1 host-source implemented and locally tested; R5-R3B installed custody, R5-R3C and R5-R3D NOT ACCEPTED.** R5-R2-R1 is scoped accepted at exact source `162edb29d60abe8e373c2e961333611d74f13717`, [original native run #44913129057](https://github.com/vjmichael/TradeBot/actions/runs/44913129057), with **235/235** source tests, **4/4** offline QEMU scenarios and independently verified artifact #14710224310 (SHA-256 `504df835b71902df69701a532f23ae3fcbb66b4718114c17d2f1bce025471ff6`). ## Engineering execution policy

- **Build on host/ordinary native CI runner, not inside QEMU.** Prepare pinned Debian root filesystem and any Python/JS compiled assets on host before booting. QEMU is reserved for installed kernel/systemd/PAM/IPC tests, truly abrupt host-QEMU SIGKILL and same-overlay recovery, and cross-version lifecycle behavior. Later physical Debian/VPS native acceptance is an independent release gate.
- **No Docker.** Batch source/staging changes with local preflight; do not push a new CI workflow trigger for every subtask. Retain the accepted R5-R2-R1 original matrix and receipts. No default-branch merge until independent release review.
- **Default PAPER, fail-closed and disabled.** Never use production credentials, access real Kraken endpoints, place orders, turn on LIVE, or claim a production installer solely from offline synthetic success.

## R5-R3A — publisher and package trust contract (source implemented)

1. Define a deterministic package manifest: publisher identity, release/version and anti-rollback epoch, permitted file inventory, hashes, exact schema compatibility, target OS/architecture, service identities and installation paths. Cryptographically bind this manifest to a reviewed signed package and a separately preprovisioned publisher trust root; the package must not install or replace its own root of trust.
2. Define protected trust-root enrollment, rotation and revocation under separate authenticated operator/administrator authority. Reject unknown/revoked signers, altered packages, manifest substitution, replay, out-of-order releases, unauthorized downgrades and swapped executable/service identities. An authenticated rollback may restore the prior *approved* release without granting arbitrary downgrade.
3. Implement host-side, read-only manifest/trust validation and deterministic negative unit cases **first**, using ephemeral fixture keys. No production signing private key may enter the repository, CI artifacts, guest disk, logs or installer payload. Retain explicit auditable version/publisher pins and refusal receipts.

**R5-R3A gate:** all exact-source host tests pass, including wrong/revoked/rotated publisher and mismatched signed inventory; no installed guest or CI batch is required to complete initial source work.

## R5-R3B — transactional installer and data-compatibility custody

1. Implement prepare/stage/verify/commit/recover phases with root-protected no-follow paths, durable file and directory fsync, explicit journal/version records and source hash pinning; never mutate live services before verification. Stop/restart only fixed authorized units with bounded readiness and safe interrupted state.
2. Keep credential-bearing encrypted vault data intact and inaccessible to packaging workers. Initially admit metadata-only, backward-compatible migrations under a reviewed schema declaration. **Do not** perform an encrypted-secret migration, key export, provider credential read or destructive rollback without a separate approved custody design and operator authorization.
3. Preserve prior encrypted state on rollback refusal; bind any later authorized migration to an independent, transactional, operator-approved state transition with audit-safe receipts. Never bypass existing one-use approval, revocation, broker/worker isolation, key custody or default-disable gates.

**R5-R3B gate:** immutable source/package, journal, rollback, data-preservation and refusal unit tests; no production secret or live provider.

Assess protected service permissions, tamper resistance, signed publisher custody, revocation, logging redaction, restore/rollback operator interaction and disaster recovery. **No LIVE admission or real trading follows automatically.** Provider-specific least-privilege, R2C browser/notification/KEK, migration and financial safeguards retain their own release gates.

## R5-R3A host-side verifier implementation (local host PASS; no CI triggered)

- New `publisher_verifier.py` (Git blob `595a4e6ffa22db8bdd226f99ddbc5013ceaea4aa`) is a **read-only Python 3 verifier**. It expects a separately provisioned canonical trust-policy byte string and independently protected installed-state byte string from a **trusted caller**, never from the candidate package. It does not write files, enroll trust, execute installer commands, enable systemd units, contact the network or authorize trading.
- Exact canonical JSON / duplicate-key refusal, strict schema and size limits, domain-separated **Ed25519** verification, SHA-256 key IDs and source payload digests, bounded O_NOFOLLOW file reads, no symlink/hardlink/undeclared files, pinned install destinations/modes and platform (`linux/x86_64`), signed service user/group declarations checked against both separately provisioned policy and unit contents, unchanged data schema and **PAPER staging scope only**.
- Policy records active/revoked Ed25519 public keys, key epoch windows, publisher identity, trust generation/epoch floor and exact target/service inventory. Installation state records last accepted release sequence, security epoch, trust generation, schema version and manifest digest. Rejects unknown issuers/keys, revoked/expired/not-yet-authorized keys, mismatched signatures or data, replay, downgrade, stale policy generation, schema migration, LIVE scope and unit identity substitution.
- New `test_publisher_verifier.py` (Git blob `458d2428ec6fee67e4f8ca2411b4bfd79b934125`) uses **ephemeral in-memory test signing keys**; no persistent signing secret or real credentials. Host-only command: `python -m unittest discover -s qualification/r2b-admission-r5-r3 -p 'test_*.py' -v`. Independent local Python 3.13.5 / cryptography 46.0.4 run passed **41/41** in ~0.06s; `python -m compileall` passed; Git blob IDs exactly matched the local tested files. This is a **local source receipt, not GitHub native CI or production installed acceptance**.
- **Explicit custody limit:** the verifier cannot establish that the supplied trust policy/installed state are genuine; production identity, immutable root custody, secure enrollment/rotation/revocation and transactional persistence must be implemented in R5-R3B. A compromised caller, mutable package between verification and installation, systemd drop-ins, credential-bearing migrations and physical installation are outside this source gate. A successful verifier result **does not install, enable, authorize LIVE or approve money movement**.

## R5-R3B-R1 protected staging implementation (local host PASS; no CI trigger)

- Added `protected_staging.py` (exact tested Git blob `1a686ce749333e6b03e64e5d86c73b5f8f7bdbc5`) and `test_protected_staging.py` (`dda073d5c1e4d4fc9ffcedc52f1cf4d46254c519`). Original R5-R3A verifier/test Git blobs are unchanged.
- **Trust and state custody:** host process reads separately preprovisioned `trust-policy.json` and `installed-state.json` from a pre-existing administrator-owned `0700` directory. Each file must be a regular single-link owner-controlled `0600` file, opened with `O_NOFOLLOW`, bounded and checked for mutation during reading. Default expected UID is **root (0)**; the test-only constructor can inject the current synthetic test UID. Linux `flock` on the protected directory serializes cooperating staging operations. The trust files never originate from the signed package.
- **Durable transaction:** an exclusive `.pending` hold is directory-fsynced before copying. The canonical private journal records `PREPARING` and `PREPARED` plus exact candidate manifest, independently read policy and release-state SHA-256 commitments. Every private staged payload and enclosing directory is synced before the journal transitions to `PREPARED`. Revalidate the **copied** signed package against unchanged policy/state, then atomically rename the stage to `ready` and fsync the protected root. No executable is installed, service changed, network contacted or vault opened.
- **Restart recovery:** reject conflicting, malformed or unsafe holds; abandon only a `PREPARING` copy using bounded no-follow cleanup; complete a `PREPARED` publish only after exact repeated signature/inventory/trust/state validation. `verify_ready` rejects tampering, revoked/stale policy and advanced release state. An explicitly trusted caller may discard a ready stage without touching installed state. Fail-closed refusal codes and no secret diagnostic data.
- **Host qualification:** original **41/41** R5-R3A tests plus **34/34** new custody, contention, tamper, crash/fault-injection and recovery tests: **75/75 total PASS**, Python 3.13.5 / cryptography 46.0.4; local `compileall` PASS. Exact source/test Git hashes above matched the tested files before publication. Command: `python -m unittest discover -s qualification/r2b-admission-r5-r3 -p 'test_*.py' -v` on ordinary Linux host. **No QEMU, Docker, production credentials, live trading or new CI workflow.**
- **Critical limit:** this is **protected read and durable staging**, not a native installed-release commit. `installed-state.json` is deliberately **not advanced by staging**; no installer receipt, authenticated policy enrollment, key-revocation custody, immutable installed handoff, fully protected root ancestor validation or post-verify installation TOCTOU guarantee is implemented here. Those demand R5-R3B-R2 host integration and subsequent native installed tests. A privileged root process or compromised caller remains out of scope, and a passing host test is NOT physical/production acceptance.
